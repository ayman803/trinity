## Idea 1: A closed-loop clock (feedback instead of a fixed formula)

**What it is.** Part A, as designed, is open-loop: it predicts how many
moves are left and divides the clock, then corrects the plan with one
fixed factor (the measured spend ratio, about 0.5). A closed-loop clock
adds feedback: before each move, compare the time actually left with
where a reference curve says it should be at this move number (for
example "spend evenly until 10% of the period remains"), and scale the
budget by a factor that grows when Trinity is ahead of schedule
(time left > plan) and shrinks when behind. A simple proportional-integral
rule: factor = clamp(1 + Kp x error + Ki x summed error, 0.5, 2.0), where
error is (time left - planned time left) / planned time left.

**Why it might work.** Control theory: an open-loop controller is only as
good as its model, and Trinity's model is known to be off by about 2x (it
spends half of what it plans), and that ratio depends on the time
control, the position type and the machine. A feedback loop removes the
need to know the ratio at all: whatever the stop rule saves is spent
later because the controller sees the surplus. This is why thermostats
measure the room instead of computing the heat needed. It also protects
against the opposite failure (running short) on unusual hardware, which
matters because CCRL testers' machines vary.

**Cheap test.** Build it as a variant of part A (same branch, one switch),
and test both against main and against tm-control at 8+0.08 and at 40/20
(the workflow now accepts 40/20). Check with 18-Time-Use.bat on the
resulting games that the unused share falls below 8% and the realised
spend tracks the reference curve; that check needs no extra games beyond
the SPRT's.

**Prediction.** Self-play +3 to +10 over main (about the same as part A
at 8+0.08, more at 40/20 where the leak is larger). Over part A alone: 0
to +3. Fraction kept against rated engines: about 50% (time use helps
against anyone, but the 40/20 rating gap suggests diminishing returns).

**Risk.** A badly tuned loop oscillates (spend too much, then starve).
Keep the gains small and the factor clamped; the hard limit stays.
In sudden death with increment the reference curve must include the
increment, or the loop will hoard it.

## Idea 2: Ablation audit of the pruning rules on Trinity's own mistakes

**What it is.** The forensics found about 180 moves where 10x time fixes
the mistake. More time helps because some line was cut too early. Which
rule cut it? Take those positions and re-search each at the SAME time as
in the game, once per pruning or reduction rule with only that rule
switched off (reverse futility, razoring, null move, late-move pruning,
futility, SEE pruning, late-move reductions; the tune build already
exposes their settings, and an extreme value disables each). Count, per
rule, how many mistakes disappear. Compare with a control run where
nothing is switched off (the same-time noise check ESTIMATES.md asks for).

**Why it might work.** This is ablation, the standard method in machine
learning and in biology (knock out one gene, see which trait changes) for
attributing an effect to a component. Today all search rules are tuned
jointly by SPSA on self-play, which finds a balance between them but
cannot say which one is responsible for the specific errors that lose to
rated engines. If one rule stands out (fixes, say, 3x more mistakes than
the control), it is the place to spend the next design effort: a gentler
version of that rule only in the situations where it misfires. If none
stands out, the mistakes are a general depth problem, and the next effort
should go to speed or the network, not search rules. Either answer saves
experiments.

**Cheap test.** CPU only, no games: about 180 positions x 8 runs x the
game's move time (about 0.3 s) = about 8 minutes on the PC with 10
workers. Needs a small extension of the forensics tool (store the
mistake positions; re-search them with a list of option settings).

**Prediction.** 0 Elo by itself; its value is choosing the next search
change. If one rule stands out, a targeted fix might give self-play +3 to
+8, kept about 40% against rated engines (search changes have
transferred poorly here).

**Risk.** Switching a rule off makes the search slower overall, so it
also "fixes" mistakes simply by looking wider; the control and the
per-rule comparison handle part of this, but a rule that is cheap and
mostly right can still look guilty. Use the ranking, not the absolute
counts.
