## A pointer for the Session (not an idea)

In the removed code, reverse futility pruning checks `eval.abs() <
TB_BOUND` before using `eval`, but razoring did not. `eval` there can be
replaced by a TT score (the bound substitution a few lines above), and a
TT score can be a mate or tablebase score. With no guard, razoring could
fire in won/lost-by-force lines and return a quiet-search score instead.
Whether that explains part of the +58 can't be known from the source
alone. It matters for two things: (1) never bring razoring back without
the same guard; (2) check that every other rule that uses this TT-adjusted
`eval` (whatever remains after the campaign) has the guard too. A missing
guard is a one-line fix, cheap to test.

## [search] Idea: sample the pruning rules' own mistakes directly (audit sampling)

**What it is.** The move-flip audit was too noisy: changing only the hash
size flips about 350 of 2000 moves. Measure each rule's error instead of
its effect on the final move. During normal searches (bench positions or
calibration-game positions, at game-like depths), whenever a pruning rule
decides to prune, with a small probability (say 1 in 200) also run the
search it skipped, and record whether the pruned result was wrong (the
real search would have returned a score on the other side of alpha/beta)
and how much work the rule saved. Per rule this gives two numbers:
error rate and nodes saved. A rule with a high error rate and a small
saving is the next removal or tightening candidate; a rule with a low
error rate and a big saving is fine as it is.

**Why it might work.** Acceptance sampling and audit sampling (quality
control in manufacturing; statistical sampling in financial audits):
check a random fraction of decisions directly instead of inferring
quality from the final product. It measures each rule in isolation, at
the point where it acts, so the noise of the whole search (hash, move
order, time) does not drown it out. Thousands of sampled decisions per
rule come from a few minutes of search.

**Cheap test.** An instrumented build (not for play), a few minutes of
CPU on GitHub or in the cloud. Check of the method first: the rule
already known to be bad (razoring, on the pre-e0da35a code) must show a
clearly higher error rate per node saved than RFP and LMP, which the
audit and the tests say are good. If it doesn't, drop the method.

**Prediction.** 0 Elo directly; it picks the campaign's next candidates.
If the ranking is sound, the next 2-3 removals or tightened margins it
points to: about +3 to +10 self-play in total, kept against rated
engines about 50% (pruning gains shrink with more time; main's 40/60 gap
is about two thirds of its 10+0.1 gap so far).

**Risk.** "Wrong" at one node does not always change the move at the
root, so a rule's error rate overstates its cost; compare rules with each
other rather than reading the rates as Elo. Sampling must use the same
depth and window as the skipped search, or the comparison is unfair.
