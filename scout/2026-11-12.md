2. Building resumable training is smaller than the 4 November note made
   it sound. Everything it needs is already in the trainer
   (trainer/src/main.rs, read today):
   - `TrainingSteps { start_superbatch: 1, end_superbatch }` (about line
     318): a resumed run is the same recipe with `start_superbatch` set
     to the saved checkpoint's number + 1 and `end_superbatch` the
     planned total. The learning-rate schedule depends only on the
     superbatch number and the planned total, so a resumed run follows
     the same cosine as an uninterrupted one.
   - `trainer.optimiser.load_weights_from_file` (used by the `average`
     and `kbcheck` paths) loads a checkpoint's weights; whether the
     optimiser's running averages come with them is the one thing to
     check in bullet's checkpoint format (optimiser_state/). If not, the
     first few hundred batches re-warm them, as with finetune.
   - The data position: the trainer already skips "already used
     positions" (the message at about line 207), so the resumed run can
     start where the data order left off instead of at the file start.
   - Checkpoints are saved every 50 superbatches by bullet's default
     (the long900 run has -850 and -900 folders); a resume from the last
     saved one loses at most 50 superbatches (25 minutes), which is
     enough; no need to change the save rate.
   So: a `resume <checkpoint dir> <planned total> <name> <start lr> <wdl>
   <data files...>` mode, plus the kb16.ps1 `-Resume` switch and a runner
   job that resumes the newest checkpoint of its tag when one exists.
   What "resumable" means here: a run planned as 1350 from the start that
   can stop and continue; not extending a finished 900 run to 1350 (that
   has a different schedule and is lowlr-tail's question).
