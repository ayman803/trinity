## Idea 1: Equal-marginal-value test of where extra time pays

**What it is.** tm-control showed that 12% more time on every move is
worth about +7. It does not say WHERE the extra time earned that. Split
it: three branches, each getting the same total extra time (about 12% of
the game's clock) but spending it in only one band of moves:
- band 1: moves 11-25 (early middlegame),
- band 2: moves 26-45,
- band 3: moves 46 and later (or by pieces: 17+ / 9-16 / 8 or fewer).
Test each against main. The band with the largest gain per extra second
is where the next time rule should put its weight; if all three are
equal, uniform spending (tm-control, part A) is already close to optimal
and further time-management work has little left to give.

**Why it might work.** Economics and operations research: a fixed budget
is spent best when the marginal value of the last unit is equal
everywhere (the equimarginal principle; Lagrange multipliers in
constrained optimisation). The time-use data hint that the bands are not
equal: Trinity spends 0.27 s per move at moves 11-20 against its
opponents' 0.40 s (a 33% shortfall), but only 0.14 s vs 0.15 s at moves
41-60 (7%). The forensics put most search mistakes in the middlegame. A
direct measure of dElo/dsecond per band replaces guessing. It differs
from the earlier "learned time allocation" idea: that one uses forensics
labels and in-search signals per move; this one uses game results only
and asks a coarser question, which SPRT can answer cleanly.

**Cheap test.** Three small branches (one multiplier active only in its
band, the same clamp as tm-control; check with the time-use tool on the
SPRT games that each band's extra time came out about equal). GitHub
SPRT at 8+0.08, bounds [0, 5], or a fixed 9000 games each so the three
Elo values can be compared side by side. Run after part A is decided (and price the result with the morning report's time-odds ruler), on
top of whatever main is then.

**Prediction.** As a measurement: one band gives at least 1.5x the gain
per second of the others (60% likely). Turned into a time rule, self-play
+2 to +6 over a uniform plan; kept against rated engines about 50%.

**Risk.** Each band gets only a third of the moves, so its effect is
small and the three Elo values have overlapping error bars (+/- 3-4 each
at 9000 games); a clear winner may need 18000 games per band. Extra time
in an early band leaves less for the end in sudden death; keep tm-plan's
safety caps.

## Idea 2: Rounding-aware quantisation of the network

**What it is.** The 1024 network is trained in floating point and then
rounded to integers for the engine. Each weight is rounded to the nearest
integer independently. That is optimal for each weight alone but not for
the network's output: small rounding errors can add up in the same
direction across the 1024 neurons. Two steps:
1. Measure: on 20,000 positions from Trinity's own games, compare the
   float network's eval with the quantised one. Report the mean and the
   95th-percentile gap in cp, by output bucket.
2. If the gap is meaningful (say mean > 3 cp, or a bucket clearly worse):
   choose, for the output-layer weights and biases (only 2 x 1024 x 8
   numbers + biases), whether each rounds up or down so that the quantised
   output matches the float output as closely as possible on those
   positions. This is a small least-squares problem solved on the CPU in
   minutes; no GPU training. The first layer can follow later if the
   output layer helps.

**Why it might work.** Signal processing and neural-network compression
research outside chess: rounding to nearest minimises each weight's error
but not the error of the sum; choosing the rounding direction to cancel
errors (as in error-diffusion dithering in images, and adaptive rounding
in model compression) reduces the output error at zero runtime cost.
Trinity's lessons say network quality transfers to rated engines better
than anything else, and this is the only network change that needs no
training run at all. The engine's speed and node count are unchanged.

**Cheap test.** Step 1 is a CPU script (float weights from the last
checkpoint vs nets/default.nnue). If the gap is under ~2 cp, stop: the
network is already quantised well enough. Otherwise build the re-rounded
network and run a GitHub SPRT at 8+0.08, bounds [0, 5].

**Prediction.** Self-play 0 to +4 (most likely about +1). Kept against
rated engines about 80% when real (it is a pure evaluation-accuracy
change). Honest expectation: the measurement in step 1 is the main value;
there is maybe a 30% chance the gap is big enough to act on.

**Risk.** Fitting the rounding to 20,000 positions could overfit to them
(use positions not used in the fit to check). If the float checkpoint was
not kept, step 1 needs the trainer's saved checkpoint 600; the averaging
tests show those exist.
