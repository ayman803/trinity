## [network] Finding first: the 2048 network that played was never scored

SPRT #23: the 2048 network lost **-29.8 +/- 4.2** to main (9000 games).
Before the test, the held-out loss said it was 1.3% better, which the new
exchange rate priced at +20-25 before its speed cost, about +5 to +15 after
it. Even with the full speed cost (31% fewer nodes per second, about -18 by
the time-odds ruler), its evaluation would have to be about 12 Elo WORSE
than main's, while the held-out loss says it is clearly better. One of the
two measurements is not measuring the network that played.

The likely gap: Net-Loss scores each training checkpoint from its FLOAT
weights (`optimiser_state\weights.bin`, netloss.ps1 line 54). Only the
older networks were scored as integer files. "Quantisation costs nothing"
was shown for the 1024 network only. The 2048 network's integer file, the
one the engine used in #23, has never been scored. Things that can break
only at double width and that no test so far exercises:
- the output layer sums twice as many terms; an integer sum or an AVX2
  partial sum that fits at 1024 can overflow or saturate at 2048 (the
  "padded with zero neurons" bench check cannot catch this, since zeros add
  nothing);
- the incremental accumulator update and the refresh cache during search,
  as opposed to the full evaluation that netloss uses per position;
- the output scale: the quantisation check found 3.4% of 1024's output
  weights above 1.0 and clipped at 127; at 2048 the trained weights may be
  larger and clip more.

**Cheap test (minutes of PC CPU, no GitHub):**
1. Run Net-Loss with the 2048 network's integer file (the `.nnue` on branch
   net-wide2048-20261015-0709) added as a network file, next to its float
   checkpoint 600. Equal losses (as for 1024: 0.006%) = the integer file is
   fine. Clearly worse = a quantisation or overflow problem; find it before
   any verdict on width.
2. In the engine, along a few hundred game moves, compare the eval from
   incremental updates with a fresh full evaluation of the same position,
   for both widths. Any difference at 2048 only = a bug in the search-time
   path.
3. Run Quant-Check.bat on the 2048 checkpoint (it reports the share of
   output weights at the clip limit).

**Prediction.** 50% that one of the three shows a fault. If a fault is
found and fixed, the 2048 network should land near what the ruler said:
self-play about -5 to +15 against main. If all three are clean, the result
stands, the ruler is not reliable for width changes, and the floor noted
in NETWORK.md (result loss misses what the search needs) is the bigger
story.

**Risk.** Low cost. The main risk is the opposite mistake: a clean check
followed by more GPU on width. If the checks are clean, park width and
move the network lane to something else.

## [network] Idea: the ruler must never price a network without a 200-game look first

**What it is.** A rule for the network lane, from today's miss. Before a
full SPRT (9000 games, a whole GitHub slot for 4 hours), play 200-400
games of the new network against main on the PC or GitHub at 8+0.08.
Continue to the full SPRT only if the score is within about 3 standard
errors of the ruler's prediction; otherwise stop and look for a bug.

**Why it might work.** Quality control in manufacturing: a cheap first-
article inspection before the full production run. #23's result (-30) was
so far from the prediction (+5 to +25) that 400 games (error about
+/- 17) would have flagged it within half an hour.

**Cheap test.** None needed; adopt it for the next network test.

**Prediction.** 0 Elo; saves about one GitHub slot-day per broken network.

**Risk.** A real but small gain can look bad in 400 games; the rule only
stops the run when the gap is very large, so false stops are rare.
