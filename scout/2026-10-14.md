## Finding first (not an idea, a likely mistake): SPRT #16 tested a copy of main

SPRT #16 (nnue-simd vs main) gave +0.15 +/- 3.71 after 9000 games. The
branch's only commit, 1b69833 "NNUE: AVX2 output layer ...", changes one
file, src/nnue.rs, and adds only the `#[cfg(test)] speed_probe` test (46
lines). It contains no AVX2 code at all (no `_mm256`, no `avx2`, no
`target_feature` anywhere in the branch's src/). A `#[cfg(test)]` block is
not compiled into the engine, so both sides of SPRT #16 were the same
program. The +0.15 is exactly what an identical pair should give.

What this means:
- The AVX2 output layer (the 83 ns vs 169 ns evaluate measured on 13
  October) was apparently never committed. Gate change 2 has not been
  tested yet; #16 should not count as a gate loss.
- Useful by-product: #16 is a free A-vs-A control. 9000 games of an engine
  against itself on GitHub came out at +0.15, so the SPRT setup shows no
  side bias.
- For the Session: confirm with `git show --stat 1b69833`, recover the AVX2
  code if it still exists anywhere, commit it, check that bench node count
  is unchanged and nodes per second rise, then re-run the SPRT.

## Idea 1: Identical-binary guard in the SPRT workflow

Plain language: before playing any games, the SPRT job compares the two
compiled engines byte for byte (a checksum of each file). If they are the
same file, the job stops and says "both sides are the same program".

Why: today's finding cost a whole 9000-game run and nearly a gate decision.
The "bench unchanged" check cannot catch this, because speed-only changes are
supposed to keep the bench node count. A checksum can. (Version strings or
build paths may make two identical programs differ slightly; if so, compare
after stripping, or compare the `bench` nodes-per-second too and warn when
the "speed" side is not faster.)

Cheap test: run the workflow once on `nnue-simd` as it is now; it should
stop within a minute.

Predicted gain: 0 Elo directly. Saves GitHub runs and wrong decisions.
Risk: a false alarm if the build is not reproducible; then fall back to a
warning instead of a stop.

## Idea 2: A time-odds ruler for pricing every speed change and time change

Plain language: SPRT #15 (tm-control) showed that 12% more thinking time on
every move is worth +6.8 +/- 2.7 self-play Elo at 8+0.08. Treat this as a
ruler: a change that makes Trinity X% faster should be worth about the same
as giving it X% more time, so its expected gain is roughly
6.8 x ln(1 + X) / ln(1.12). Add two more points to the ruler cheaply (main
with 25% and 50% more time against main, 3000 games each on GitHub) so the
curve is measured, not assumed.

Why: it turns every speed idea into a number before any test, which is what
rule 4 (predictions vs results) needs, and it chooses SPRT bounds that the
change can actually reach. Example: the AVX2 layer's measured +7.3% nodes
per second on real game positions prices at about +4 self-play, so bounds
[0, 5] with a 9000-game cap give it well under even odds of passing; a
longer run or bounds [0, 3] fit it better. It is the same idea as a
dose-response curve in pharmacology: measure the response at a few doses
once, then predict from the dose.

Cheap test: two GitHub runs with a time-odds option (if the workflow cannot
give one side more time, a temporary branch that multiplies the soft and
hard limits does the same, like tm-control did).

Predicted gain: 0 Elo directly; better predictions and fewer underpowered
tests. Fraction kept against rated engines: the ruler itself must be checked
once with a calibration run at 1.25x time (expect less than self-play,
perhaps 50-70%, as with other self-play numbers here).
Risk: speed and time are not quite the same thing (a faster evaluation also
changes how much of each move is spent in the network), so treat the ruler
as +/- 50%.
