## Measured and dropped (search): nodes to a fixed depth, cloud builds of today's main

Method as on 6 November: scratch builds of main and of each variant,
`bench` (depth 10, 16 MB, table cleared per position), 40 held-out game
positions at depth 11, and a new "replay" check that is closer to a game:
main plays 8 fixed 40-ply lines from held-out positions, then each build
searches every ply of every line to depth 10 in one process, so the
table carries over from move to move as in a game (16 MB, and 1 MB to
imitate the table pressure of a long time control).

| Candidate | What it changes | Result (nodes, variant / main) | Verdict |
|---|---|---|---|
| no-killerclear | killers of the next ply are not cleared at every node (killers then carry across cousin subtrees, not only siblings) | bench 1.159 (16% MORE nodes) | the clearing is right; dropped |
| no-multicut | the singular search no longer returns s_beta when another move also beats beta | bench 1.044 | multi-cut saves about 4% of nodes; a removal would have to be worth more than that; dropped |
| tt-depth | a same-position entry is replaced only by an equal or deeper result (today: also by one up to 3 plies shallower) | bench 1.063; 1 MB depth 11 median 1.049; replay 16 MB 1.002 | worse or equal; dropped |
| tt-coll | on a collision keep a current-search entry that is 4+ plies deeper (today: always replace) | bench 1.001; 1 MB depth 11 1.034; replay 16 MB 0.976, 1 MB 1.107 | a wash; dropped |
| tt-2way (prototype) | two slots per position, the less valuable one replaced (empty, then old search, then shallower) | bench 0.977; replay 16 MB 1.020, 1 MB 1.051; 1 MB depth 11 median 1.097 | better only at low pressure, worse under game pressure; dropped |

What this says about the engine: the first-commit table rules (replace
on every collision; a shallower result up to 3 plies replaces a deeper
one) beat every depth-preferring variant, and the two-slot prototype did
not help either: fresh entries are worth more than deep ones here. The
killer clearing and multi-cut are earning their keep. None of the five
gets a game.

Noise floor, for future offline checks: with a fixed line, a table change
of any kind moves the node count of a single 40-ply line by up to 20%
either way (per-line ratios 0.77 to 1.38 for a change that nets -2%),
the same chaos the ablation audit found. Eight lines and the bench
together resolve about 3-5%. Offline node counts can only screen for
large effects (no-checkext's 25%); small effects need games.

## [network] equal-passes data test: more positions at the same number of passes

**What.** The more-data network (17 October) had two changes against
main's run, not one: 5.6 billion positions instead of 3.65 (the change
meant) and 10.7 passes over them instead of 16.4 (the same 600
superbatches spread over more data). It lost -10.85 +/- 4.08. long900
then showed that passes alone matter: 24.6 passes gave +5.65 over 16.4,
same data and seed. Put together, the three results line up with the
number of passes (10.7: -11; 16.4: 0 +/- 5.5 across three starts; 24.6:
+5.65), so the more-data result may have measured the fewer passes, not
the extra positions. The data lever has not actually been tested at this
network size.

**Test.** Same recipe and seed as long900, the 5.65 billion positions of
the more-data run (if second-1/second-2.data are still on the PC; the
newdata script kept its .data files and deleted only the raw parts),
1390 superbatches so each position is seen about 24.6 times, as in
long900. One change against long900: the data. Head-to-head against
long900's network on the same search. Cost: about 11.6 hours of GPU, so
it needs the resumable training of 4 November (two nights, or a night
plus idle daytime); without it, it cannot run. Order: after lowlr-tail
(which tells whether the passes are the lever at all) and after long1350
if the Session prefers length first; one network experiment at a time.

**Why it might work.** At equal passes the only difference is 55% more
distinct positions; the 2048 run showed the networks memorise this file
(training loss 2.5% better than held-out), and memorisation is what more
distinct positions reduce. The earlier lesson "more Leela data did not
pay" came from refinement runs on a converged network and from the
confounded 600-superbatch run, not from a from-scratch run at equal passes.

**Prediction.** Self-play vs long900 -4 to +8; about 20% to pass [0, 5]
(scaled 0.6x per the forecast review). Kept against rated engines: about
50% (the 1024 network and king buckets carried over almost fully; data
refinements did not).

**Risk.** Two nights of GPU for one answer; if lowlr-tail shows the gain
is the low-rate tail rather than the passes, the passes argument weakens
and this test should wait. Disk: 5.65 billion positions are already on
disk if kept; nothing new to convert.
