## [network] Idea 1: A loss-to-Elo exchange rate, fitted from Trinity's own networks

**What it is.** Tonight Net-Loss.bat scores every checkpoint of the 1024
and 2048 runs on the same held-out positions (calibration games, pure-result
loss). Add the networks whose Elo is already known, score them the same way,
and fit one line: Elo difference = k x (held-out loss difference).
Known points already in ESTIMATES.md:
- 1024 checkpoint 600 vs the averaged nets 550+600 and 450-600: about 0 Elo
  (SPRT #11 +0.4, #12 -1.3);
- 1024 (main) vs the 512 king-bucket net it replaced: +80 self-play;
- the 1024 checkpoints 450 / 500 / 550 vs 600 can be added with a few short
  SPRTs if more points are needed.
With k known, every future network (2048, a longer run, a second Leela file,
a re-rounded quantisation) gets an Elo prediction from one minute of CPU
before any GitHub time is spent, and rule 4 gets a measured basis for
network predictions instead of the 1.1x-10x guesses so far.

**Why it might work.** In machine learning generally, held-out loss tracks
downstream quality closely within one model family and one data source;
the relation is smooth even when single test results are noisy. A ruler
like this worked for search time yesterday (time-odds: the fast code was
priced at about +3 and the combined test agreed). The held-out positions
come from games against rated engines, so the line is closer to the CCRL
scale than self-play is.

**Cheap test.** One extra run of Net-Loss on the 512 net (if its file is
still in an old net-... branch) and on the two averaged nets (their
branches exist). Minutes of PC CPU, no GitHub. Check: the averaged nets
must come out within noise of checkpoint 600 (they tested at ~0 Elo);
if they don't, the loss measure is not sensitive enough to use.

**Prediction.** 0 Elo directly. Usefulness: predicts the 2048 verdict
within +/- 10 self-play Elo (60% likely). Fraction kept against rated
engines: not applicable (a measuring tool).

**Risk.** Two or three reliable points only; the 512 -> 1024 jump also
changed speed (-28%), so the line mixes eval quality and speed: correct
it with the time-odds ruler (0.57 Elo per 1% speed) before fitting.

## [network] Idea 2: Don't judge width with the narrow network's learning rate

**What it is.** The 2048 run copies the 1024 recipe exactly, including
LR 0.001. If the 2048 run comes out flat or worse, do NOT conclude "width
is used up" yet. First rerun 2048 with the hidden-layer and output-layer
learning rate scaled by about 1/2 (0.0005) or 1/sqrt(2) (0.0007), same
data and length, and compare held-out loss at superbatch 300 against
tonight's run.

**Why it might work.** Theory and practice of training wide networks
outside chess: with Adam-type optimisers, the weights feeding from a wider
layer each receive a gradient of about the same size, so the same learning
rate moves the layer's output roughly twice as much when the layer is
twice as wide. The best learning rate for those weights therefore shrinks
roughly in proportion to width; a recipe tuned at one width is too hot
at double the width. The symptoms would be a loss curve that drops fast
early and then stalls above the 1024 curve, or more noise between
checkpoints. The history here already shows how sensitive these networks
are to the rate (king buckets refined at 0.0005: -13.8; at 0.0002: -3.8).

**Cheap test.** Read tonight's per-superbatch loss log first (no cost):
if 2048 is below 1024 at every superbatch, skip this idea. Only if it
stalls or ends near 1024: one more overnight GPU run at the scaled rate
(8-10 h), judged on held-out loss at superbatch 300 and 600 before any
SPRT.

**Prediction.** Needed only if tonight's run disappoints (about 30%
likely, from Coder 2's 70% pass estimate). In that case the scaled rate
recovers +5 to +15 self-play of the width's value; kept against rated
engines about 70% (capacity has transferred well here: king buckets 1.1x,
1024 network about 1.6x).

**Risk.** A lower rate under the same cosine schedule may under-train in
600 superbatches; if the held-out loss at 300 is worse than tonight's,
stop at once. It costs one night of the PC's GPU.
