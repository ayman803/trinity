## Idea 1: Bucket spread (a second opinion from the network it already has)

**What it is.** The network ends in 8 output buckets, picked by how much
material is on the board. Each eval uses one. The idea: also compute the
answer of the neighbouring bucket (the one for one step more or less
material) and treat the *gap* between the two answers as a measure of how
unsure the evaluation is. Use that gap where corr-unsure uses the
correction size today: reduce less (LMR) when the gap is big, and possibly
prune less.

**Why it might work.** Weather forecasting runs an *ensemble* of slightly
different models; when they disagree, the forecast is trusted less. Two
output buckets are two slightly different "experts" reading the same
board features. Where they agree, the position is probably well
understood; where they disagree, the eval is sensitive to the material
framing, which is exactly where a shallow search is most likely to be
misled. Trinity's own data says uncertainty-aware search pays here:
corr-unsure gave +10.8, three times the prediction. The correction size
only becomes informative after the position family has been seen in this
search; bucket spread is available from the first visit.

(I considered training a dedicated "how wrong am I" output instead. Dropped
it: it is more trainer work and I am not confident it is free of
resemblance to work elsewhere.)

**Cheap test.**
1. Offline check first (no games, a few CPU minutes): on ~10,000 positions,
   compute the bucket spread and |static eval - depth-12 search score|. If
   the correlation is near zero, stop here: the signal is noise.
2. If it correlates: SPRT on GitHub, 8+0.08, bounds [0, 5], branch where
   corr-unsure's trigger becomes "correction >= 12 cp OR spread >= X"
   (X = the 80th percentile from step 1).
- Cost per eval: one extra output dot product on activations already
  computed; expect about 1-3% fewer nodes per second.

**Prediction.** Self-play -2 to +8. Fraction kept against rated engines:
about half (uncertainty-type changes have not been calibrated yet; corr-unsure
was never measured alone).

**Risk.** Neighbouring buckets may differ for boring reasons (they were
simply trained on different positions), giving a noisy signal. The
offline check exists to catch that before any games are spent. The
slowdown could eat a small gain.

## Idea 2: Weight averaging of the last training checkpoints

**What it is.** The 1024 network came from one long training run (600
superbatches). If the trainer saved checkpoints along the way, average
the weights of the last few (for example the last 5, spaced 20
superbatches apart) and quantise the average into a new network. No GPU
training at all.

**Why it might work.** From statistics and machine-learning research
outside chess (Polyak-Ruppert averaging, later "stochastic weight
averaging"): the noisy end of a training run wanders around a good
region; the average of several late points sits nearer its centre and
usually generalises better than any single point. Trinity's own lessons
say improvements to *how a network is trained* transfer to rated engines
better than more data does, and this is the cheapest such change
possible.

**Cheap test.** One CPU script (average float checkpoints, quantise,
build), then SPRT on GitHub, 8+0.08, bounds [0, 5]. Before that, a sanity
check: the averaged network's bench must change and its eval of the
start position should be close to main's.

**Prediction.** Self-play 0 to +8. Fraction kept: about 70% (network
improvements have transferred 0.9-1.0x when they were real, but
refinement-type changes have transferred poorly).

**Risk.** (a) The checkpoints may not have been kept; then it costs nothing
to find out, but the idea waits for the next long training run (save
checkpoints from now on). (b) The cosine learning rate already ended near
zero, so the last checkpoints may be almost identical and the average
changes nothing. Averaging checkpoints from earlier, when the rate was
higher (e.g. superbatches 450-600), is the stronger version and the
riskier one.

## Idea 3: Loss forensics (find out why Trinity loses before guessing fixes)

**What it is.** Reliability engineers do a failure analysis (FMEA,
Pareto chart) before redesigning a part. Do the same with the lost games
that 5-Calibrate.bat now saves in games/. For each loss, a script finds
the "turning point": the first Trinity move after which its own reported
eval fell by, say, 100 cp within a few moves and never recovered. Then:
- re-search each turning-point position for 10x the game's time. If
  Trinity now finds a different move whose score holds up, the loss is a
  **search/time** loss; if not, it is an **evaluation** loss (it did not
  understand the position at any depth).
- tag each turning point by phase (piece count), by bucket, and by whether
  the opponent's move just before was a capture, check or quiet move.
Count the categories. The biggest bar says where the next week of work
should go (network, search, or time management).

**Why it might work.** Every gain so far was chosen top-down from general
expectations; search tweaks borrowed as ideas gave ~0. A Pareto count of
Trinity's own failures is direct evidence. It also explains the unsolved
puzzle in ESTIMATES.md: Trinity rates ~30 higher at 40/20 than at 10+0.1.
If most losses are "fixed by 10x time", time allocation is the lever for
the 40/15 list.

**Cheap test.** CPU-only. The 1.0.0 calibration's games (including
1,040 losses) are already on the PC in `C:\Trinity\sprt\results`
(`2026-10-12_19-36_calibration_*`), so this can start now; later losses arrive in
games/ automatically. 200 losses would be enough. Running the
re-searches is ~1 hour on one PC core set. No SPRT needed.

**Prediction.** 0 Elo by itself. Its value is choosing the next change;
I would expect it to save at least one failed experiment.

**Risk.** Eval comments in the PGN are from Trinity's point of view at its
own depth, so the "turning point" can be found too late (the real mistake
came earlier and Trinity did not see it yet). Mitigation: also search the
3 positions *before* each turning point at 10x time.
